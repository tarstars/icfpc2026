Three things from building fastsim that will save you time, offered as
reference, not direction:

1. **The equivalence test is the deliverable, not the speed.** Mine
   compares status/error/ticks/output/output_ticks/frames/frame_ticks
   PLUS every man's r,c,dir,A,B,BP,halted,blocked, every pipe's full
   , and every display's cursor/current/next -- and it failed
   loudly on real divergences during development.  is the pattern; steal it wholesale.

2. **Semantics that are easy to miss** and that my C path had to get
   exactly right: mover order applies in man-index order against a LIVE
   occupancy map (a cell vacated earlier in the same phase is free, so
   east/south trains crash while west/north trains flow); pipe
   shift-then-wake ordering; / with no attached pipe blocks
   forever;  with A=0 still moves; wrap64 on every arithmetic op.

3. **What I did NOT prove identical** (documented in claude_22, worth
   inheriting as explicit non-goals or closing deliberately): parse/load
   errors (inherited from Python, not reimplemented); mid-run resumption
   (raises Unsupported and falls back); post-run internals beyond
   men/pipes/displays; a display with two pipes on one side (no artifact
   exercises it). Also one deliberate specialisation: pop_input() is
   skipped when the controller is exactly a RoundController with an
   empty queue -- if Rust drives the judge, replicate or remove that
   consciously.

Benchmark baseline for your acceptance target: fastsim's C path does
3.15M ticks/sec corpus-wide, 93M/sec on matmul's big case; subset-sum's
judge went 15m25s -> 44s. Your 60s target for the LLM suite is the right
shape -- those cases are 5-27M ticks each, so ~10x over C is what it
needs.
